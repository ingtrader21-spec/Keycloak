# Security test matrix

Release evidence must cover login/logout, registration policy, verification, reset, MFA and required actions; discovery, JWKS, Authorization Code with PKCE, Client Credentials, refresh and logout; audience, scope and cross-client isolation; rejection of wildcard redirects, implicit/password grants, wrong issuer/audience, expired and tampered tokens; container/database/reboot recovery; and backup, restore, rollback and partial APPLY.

Kong certification must prove one authorized request succeeds and missing, malformed, expired, wrong-issuer, wrong-audience, insufficient-scope, invalid-signature and disabled-client requests fail. Untested rows are `BLOCKED` or `NOT RUN`, never `PASS`.

`scripts/certify-kong.sh` executes this matrix without changing client configuration and writes a mode-0600 JSON evidence file. Set `DEPLOY_ENVIRONMENT` explicitly to `staging` or `production`; all Keycloak token and Admin API calls use that environment's checked-in endpoint contract. No production endpoint fallback is permitted. `KONG_TEST_URL` must be the reviewed HTTPS protected route for the same environment.

Supply `CERT_CLIENT_ID`, `CERT_CLIENT_SECRET`, `EXPECTED_AUDIENCE`, `EXPECTED_SCOPE`, `KONG_EVIDENCE_FILE` (an absolute output path), and the reviewed `KONG_TOKEN_WRONG_ISSUER`, `KONG_TOKEN_WRONG_AUDIENCE`, `KONG_TOKEN_INSUFFICIENT_SCOPE`, and `KONG_TOKEN_EXPIRED` fixtures through the approved secret delivery mechanism. Tokens and credentials must never be committed or pasted into evidence.

The disabled-client row is mandatory. Supply `DISABLED_CLIENT_ID` and its current `DISABLED_CLIENT_SECRET`, plus a separate `KC_CERT_ADMIN_CLIENT_ID` / `KC_CERT_ADMIN_CLIENT_SECRET` identity permitted to read the fixture's representation and current credential in the selected realm. Keep this identity separate from the restricted Klyrow GitOps identity; do not expand that identity's privileges for certification. Arrange the fixture and scoped read access through the existing operator approval process before running the test.

`scripts/certify_disabled_client.py` authenticates the read-back identity, finds exactly one matching disabled confidential service-account client, compares its current credential with the tested secret, requests a token, and requires an OAuth client rejection. It then repeats the authenticated state and credential reads. Missing clients, mistyped credentials, denied reads, changed state, redirects, network errors and malformed responses fail certification. Caller-supplied JSON is no longer accepted as proof. The helper never creates, enables, disables or rotates a client. The evidence contains environment, issuer, fixture identifiers, timestamp and rejection status, without credentials or tokens.

This proves the fixture state and credential at the two read-back points; it does not replace controlled canary/rollback evidence or the full Middleware matrix in `config/certification/service-identity-matrix.json`.
